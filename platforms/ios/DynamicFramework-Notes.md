# Dynamic iOS framework for cvextern: findings

Status: **not started.** On 2026-11-05 we decided to keep the static framework for now. These
notes record what was learned so the work can resume later.

## Current setup

- `libs/iOS/libcvextern_ios.xcframework` contains **static** libraries (`libcvextern_iphoneos.a`
  for the device, a simulator `.a` alongside).
- The .NET runtime project links it as a `NativeReference` with `Kind=Static`, `SmartLink=True`
  and `ForceLoad=True` (`Emgu.CV.Runtime/Maui/iOS/Emgu.CV.runtime.maui.ios.csproj`).
- Managed code calls it with `ExternLibrary = "__Internal"`, generated by
  `cmake/CvInvokeEntryPoints.cmake` / `cmake/CvInvokeEntryPoints.cs.in`. The same applies to
  Unity on iOS (`UNITY_IPHONE`).

## Why consider a dynamic framework

- **Symbol isolation.** A dynamic framework keeps its own copies of libpng, libjpeg, zlib and so
  on private to itself. That would remove the class of duplicate-symbol bugs with Unity's
  built-in libraries that `EMGU_CV_PNG_PREFIX` / `EMGU_CV_JPEG_PREFIX` currently work around
  (see CLAUDE.md, "Native C++ (Unity iOS)"), including future clashes with other libraries. To
  get the full benefit, export only the `cve*` functions.
- **Faster app builds.** Every app build re-links the ~108 MB static library. An embedded
  framework is only copied and signed.

## Costs and open questions

- **App size:** probably a small difference, since `ForceLoad=True` already pulls in the whole
  static library. Needs measuring.
- **Launch time:** dyld has to load one large framework at startup. Needs measuring on an older
  device such as the iPhone X.
- **Library name:** `"__Internal"` only works for static linking. A runtime resolver could try
  the embedded framework first and fall back to the app binary, so one `Emgu.CV.dll` works with
  both variants. Check whether IL2CPP can use the same approach.
- **Packaging:** the framework needs an `Info.plist`, a minimum OS version matching
  `cmake/ios_min_version.txt`, embedding and signing in the app, and ideally a privacy manifest.

## How Unity handles dynamic iOS plug-ins

From the Unity 6000.6 / 7000.0 manual:

- `.framework` and `.xcframework` are supported iOS plug-in types. Files under
  `Assets/Plugins/iOS` are enabled automatically, and XCFrameworks are the recommended format for
  multiple architectures.
- Dynamic code must be copied into the app with the **Add to Embedded Binaries** plug-in setting
  ("required for dynamically loaded libraries (`.dylib`) [and] bundles and frameworks that
  contain dynamically loaded code"). The setting is stored in the plug-in's `.meta` file, which
  Emgu.CV.Unity already ships, so it can be preset there.
- `DllImport` uses `"__Internal"` for code linked into the app binary, and "the library name"
  for a dynamic library (`"MyPlugin"` for `MyPlugin.dylib`). **The manual doesn't say what name
  to use for a `.framework`.** That has to be tested on a device.
- `.dylib` files are simulator-only ("Apple doesn't permit publishing applications that contain
  `.dylib` files"), so the dynamic build must be a `.framework` inside an `.xcframework`.
- Signing, Mac Catalyst, visionOS and the Unity version that added framework support aren't
  covered.

## Suggested prototype when resuming

1. Add an opt-in CMake option, e.g. `-DEMGU_CV_IOS_DYNAMIC=ON`, that builds `cvextern` as a
   framework (exporting only `cve*`) and assembles a framework-based xcframework next to the
   static one.
2. Add the runtime library resolver, and a `NativeReference` with `Kind=Framework` for the
   dynamic variant.
3. With the MAUI demo on the iPhone X, compare app size, launch time and app link time against
   the static build.
4. Test Unity iOS on the M1 with Unity 6: an embedded framework via the `.meta` setting, and the
   `DllImport` name IL2CPP needs for it. The Intel Mac only has Unity 2020.3, 2021.3 and 2022.2.
